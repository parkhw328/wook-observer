# 프로젝트 규칙

## 관리 문서

- 개발 지침은 `rules/rules.md`, 요구사항과 구현 상태는 `rules/requirements.md`, 버전 이력은 `rules/versions.md`에서 관리한다.
- 작업 전 세 문서를 읽고 요구사항 변경과 구현 결과를 함께 갱신한다. 사용자 지시가 기존 문서보다 우선한다.
- 사용자와 개발자가 공유하는 루트 `resources/`는 Git에 추가하지 않는다. `git add -f`로도 추가하지 않는다. 애플리케이션 설정용 `src/main/resources/`는 별개이며 추적한다.
- 기존 `AGENTS.md`는 사용자의 보존 지시에 따라 수정하지 않는다. 이후 구체화된 기술·운영 지침은 이 문서와 README를 따른다.

## 기술 및 배포

- Java 21 계열의 **21.0.13 이상**을 최소 빌드·실행 기준으로 한다. 컴파일 대상은 Java 21이며 다른 LTS 계열 지원은 별도 검증 후 결정한다.
- Spring Boot와 Maven Wrapper를 사용하고, `java -jar`로 실행되는 단일 실행 JAR를 배포한다.
- 수집기, 데이터 모델, 분류, 보고서 생성을 분리한다. Java 들여쓰기는 4칸, YAML·Markdown은 2칸을 사용한다.
- Linux 호스트에서 실행하는 수집기를 우선 지원한다. 원격 Docker 또는 격리된 PID 네임스페이스를 로컬 호스트로 오인하지 않는다.

## 분석 및 문서화

- 분석 범위는 호스트 → 실행 프로세스 → 런타임/JVM → 라이브러리와 Docker → 컨테이너 → 내부 서비스의 연결 관계다.
- 애플리케이션·웹·데이터베이스·캐시·메시징·인프라·기타 등 **서비스 직군별**로 분류한다. 자동 분류는 근거를 기록하고 설정으로 변경할 수 있게 한다.
- 각 직군의 **프로세스 명세**, **오픈소스 명세**, **컨테이너 명세**를 별도 문서로 생성하고 요약 문서에서 연결한다. PID, 컨테이너 ID, 라이브러리 경로로 관계를 추적할 수 있어야 한다.
- 오픈소스 명세에는 식별된 이름·버전·출처를 기록한다. 라이선스, 실제 로딩 여부 등 확인하지 못한 정보는 추정 사실과 구분한다. 파일명으로 추정한 버전은 명시한다.
- 수집 시각, 근거, 실패·미지원·권한 부족·제한에 의한 누락을 남긴다. 수집 실패를 빈 결과나 정상 분석으로 표시하지 않는다.

## 운영 및 검증

- 기본 수집은 읽기 중심이다. 프로세스 종료, 컨테이너 변경, 임의 명령 실행, 힙 덤프, 강제 GC, 에이전트 주입을 수행하지 않는다.
- 환경변수 값, 전체 명령행, 임의 JVM 시스템 속성을 보고서에 노출하지 않는다. 필요한 메타데이터를 선별한다.
- 명령 실행 시간과 수집량을 제한하고 일부 수집 실패가 전체 문서 생성을 막지 않게 한다.
- 테스트는 JUnit 기반으로 작성한다. Docker·JVM 경계는 고정 fixture로 검증하고 실제 환경 검증 결과와 구별한다.
- 커밋은 `feat:`, `fix:`, `docs:`, `test:`, `chore:`와 명령형 요약을 사용한다. PR에는 변경 목적·검증·미지원 범위를 적는다.

## 버전 정책

- `대.중.소`의 세 정수 형식과 Git 태그 `v대.중.소`를 사용한다.
- 대: 호환성을 깨는 변경. 중: 호환성을 유지하는 기능 추가. 소: 버그 수정·문서·빌드 개선.
- 대 또는 중 버전을 올리면 하위 숫자는 0으로 초기화한다. `pom.xml`, 배포 JAR, 버전 이력의 버전을 일치시킨다.
- `0.0.0`은 프로젝트 시작 기준이며 첫 동작 가능한 수집·보고서 버전은 `0.1.0`으로 관리한다.
