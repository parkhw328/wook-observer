# 프로젝트 규칙

## 관리 문서

- 개발 지침은 `rules/rules.md`, 요구사항과 구현 상태는 `rules/requirements.md`, 버전 이력은 `rules/versions.md`에서 관리한다.
- 작업 전 세 문서를 읽고 요구사항 변경과 구현 결과를 함께 갱신한다. 사용자 지시가 기존 문서보다 우선한다.
- 사용자와 개발자가 공유하는 루트 `resources/`는 Git에 추가하지 않는다. `git add -f`로도 추가하지 않는다. 애플리케이션 설정용 `src/main/resources/`는 별개이며 추적한다.
- 기존 `AGENTS.md`는 사용자의 보존 지시에 따라 수정하지 않는다. 이후 구체화된 기술·운영 지침은 이 문서와 README를 따른다.

## 기술 및 배포

- 중앙 웹서비스의 구현 언어는 고정하지 않는다. 가용 메모리·CPU·동시 점검·대용량 보고서의 실측과 유지보수 비용을 근거로 Python 등 다른 구현도 선택할 수 있다. 전환 시 API·DB·인증·암호화·보고서·폐쇄망 배포 호환성을 검증한다.
- 현재 구현은 Spring Boot와 Maven Wrapper이며 Java 21 계열의 **21.0.13 이상**을 최소 빌드·실행 기준으로 한다. Java 구현을 유지하는 동안 컴파일 대상은 Java 21이다.
- 중앙 웹서비스는 런타임을 포함한 Docker 이미지와 PostgreSQL로 배포한다. 현재 제공하는 일회성 실행 JAR은 호환성을 유지하며, 런타임 전환 판단은 `docs/runtime-decision.md`에 기록한다.
- 수집기, 데이터 모델, 분류, 보고서 생성을 분리한다. Java 들여쓰기는 4칸, YAML·Markdown은 2칸을 사용한다.
- Linux 호스트에서 실행하는 수집기를 우선 지원한다. 원격 Docker 또는 격리된 PID 네임스페이스를 로컬 호스트로 오인하지 않는다.
- 대상 서버에 Java가 있다고 가정하지 않는다. 중앙 서비스에서 SSH로 Linux 기본 정보를 수집하고 JVM·JAR 상세는 실제 서비스와 도구·권한이 있을 때 추가한다. 도구를 자동 설치하지 않는다.
- 폐쇄망 반입 대상은 Linux x86_64이며 Docker Engine·Compose가 이미 설치되어 있다. 앱·DB 이미지 전체 레이어, 취약점 데이터·출처·해시, 실행 설정과 설치 안내를 함께 제공한다. 반입 후 외부 pull·빌드 없이 시작하고 호스트 Java·Python·OpenSSL을 요구하지 않는다.
- 배포 묶음은 `resources/offline/`에 보관하고 Git에서 제외한다. 기존 `.env`, DB·계정·SSH 키·점검 보고서를 담지 않으며 새 설치의 비밀번호와 암호화 키는 현장에서 생성한다. 외부 통신을 차단한 별도 환경에서 설치·데이터 반영을 검증한다.

## 웹서비스 및 취약점 관리

- DB에 사용자, SSH 대상, 점검 이력·스냅샷, CVE/CCE/내부 정책, 갱신 설정·이력을 저장한다. 대상 등록 후 비동기로 점검하고 저장된 결과를 다시 다운로드한다.
- ADMIN은 계정·연결·업데이트를 관리하고 USER는 등록된 전체 대상의 점검·조회 권한을 갖는다. 세션 인증·CSRF 보호·비밀번호 해시를 사용하며 계정 비활성화 및 권한·비밀번호 변경 시 기존 세션을 무효화한다.
- SSH 개인 키·접속 비밀번호·키 암호·root/sudo 전환 비밀번호는 DB에 암호화하고 API로 반환하지 않는다. 호스트 키는 직접 입력하거나 조회한 지문을 명시적으로 확인해 등록하며 자동 신뢰는 제공하지 않는다.
- 접속 키/비밀번호와 서버 호스트 키의 역할을 구분한다. 일반 계정 점검 또는 선택한 su/sudo root 전환을 지원하고 UID 0을 확인한다. 전환 실패를 일반 권한 점검 성공으로 처리하지 않는다. 비밀번호 값은 명령행·환경변수·로그·보고서에 넣지 않는다.
- 웹은 한글 Noto Sans KR, 영문·숫자 JetBrains Mono를 로컬 파일로 제공한다. 기본 본문·입력 18px, 표·안내 16px 수준의 큰 글자를 사용하고 모바일·확대 화면을 검증한다. 런타임에 외부 폰트/CDN을 호출하지 않는다.
- 폐쇄망에서 외부 접속 없이 기동한다. 반입 JSON/ZIP과 관리자가 허용한 내부 HTTPS 미러로 CVE·CCE 데이터를 갱신한다. 정기 실행은 기본 비활성화하고 관리자 화면에서 설정한다.
- 데이터 전체 검증 후 트랜잭션으로 반영하고 실패 시 기존 데이터를 유지한다. 출처·수정/반영 시각·SHA-256·개정 번호·철회 정보를 보존한다.
- CVE는 정확한 패키지 식별자·버전과 영향 범위를 대조한다. CCE는 적용 플랫폼과 실제 설정을 확인하는 지원 규칙이 있어야 판정하며 자체 정책 ID와 구별한다.
- 보고서에 `취약점발견`, 판정 근거·범위와 데이터 개정 정보를 표시한다. 데이터/권한/도구 부족을 미발견으로 처리하지 않는다. 버전 일치를 실제 악용 가능성 확정으로 표현하지 않는다.
- 현재 중앙 앱은 단일 인스턴스로 운영한다. 다중 인스턴스 작업 큐·클러스터 일정 조정은 별도 구현 없이는 지원으로 표시하지 않는다.

## 분석 및 문서화

- 분석 범위는 호스트 → 실행 프로세스 → 런타임/JVM → 라이브러리와 Docker → 컨테이너 → 내부 서비스의 연결 관계다.
- 애플리케이션·웹·데이터베이스·캐시·메시징·인프라·기타 등 **서비스 직군별**로 분류한다. 자동 분류는 근거를 기록하고 설정으로 변경할 수 있게 한다.
- 각 직군의 **프로세스 명세**, **오픈소스 명세**, **컨테이너 명세**를 별도 문서로 생성하고 요약 문서에서 연결한다. PID, 컨테이너 ID, 라이브러리 경로로 관계를 추적할 수 있어야 한다.
- 동일 스냅샷의 요약·호스트·직군별 명세·JVM 속성·컨테이너 연결·수집 오류와 Markdown·JSON 원문을 통합한 `report.xlsx`도 제공한다. 폴더 출력과 ZIP에 포함하고 단독 다운로드를 지원한다.
- XLSX는 직군별 프로세스·오픈소스·컨테이너 시트를 구분한다. 필터·고정 헤더·내부 이동 링크를 제공하고 긴 원문은 셀 제한에 맞춰 분할 보존한다. 수집한 문자열을 수식으로 실행하지 않는다.
- 오픈소스 명세에는 식별된 이름·버전·출처를 기록한다. 라이선스, 실제 로딩 여부 등 확인하지 못한 정보는 추정 사실과 구분한다. 파일명으로 추정한 버전은 명시한다.
- 수집 시각, 근거, 실패·미지원·권한 부족·제한에 의한 누락을 남긴다. 수집 실패를 빈 결과나 정상 분석으로 표시하지 않는다.
- OS 배포판과 실행 커널을 구분하고 `uname -a/-r/-v/-m`, `/etc/os-release`, `/etc/redhat-release`, `/proc/version`을 근거와 함께 남긴다. 릴리스 파일을 셸 코드로 실행하지 않는다.
- 설치 RPM의 이름·Epoch·버전·Release·아키텍처를 호스트 명세로 분리한다. 여러 설치 버전과 아키텍처를 보존하고 서비스 사용·실제 로딩·취약점 판정으로 추정하지 않는다. 도구 없음·시간/수집량 제한·오류·이전 스냅샷 미수집을 구분한다.

## 운영 및 검증

- 기본 수집은 읽기 중심이다. 프로세스 종료, 컨테이너 변경, 임의 명령 실행, 힙 덤프, 강제 GC, 에이전트 주입을 수행하지 않는다.
- 환경변수 값, 전체 명령행, 임의 JVM 시스템 속성을 보고서에 노출하지 않는다. 필요한 메타데이터를 선별한다.
- 명령 실행 시간과 수집량을 제한하고 일부 수집 실패가 전체 문서 생성을 막지 않게 한다.
- 테스트는 JUnit 기반으로 작성한다. Docker·JVM 경계는 고정 fixture로 검증하고 실제 환경 검증 결과와 구별한다.
- 커밋은 `feat:`, `fix:`, `docs:`, `test:`, `chore:`와 명령형 요약을 사용한다. PR에는 변경 목적·검증·미지원 범위를 적는다.

## 버전 정책

- `대.중.소`의 세 정수 형식과 Git 태그 `v대.중.소`를 사용한다.
- 대: 호환성을 깨는 변경. 중: 호환성을 유지하는 기능 추가. 소: 버그 수정·문서·빌드 개선.
- 대 또는 중 버전을 올리면 하위 숫자는 0으로 초기화한다. `pom.xml`, 배포 JAR, 버전 이력의 버전을 일치시킨다.
- `0.0.0`은 프로젝트 시작 기준이며 첫 동작 가능한 수집·보고서 버전은 `0.1.0`으로 관리한다.
- 이미 배포된 바이너리를 그대로 반입 묶음으로 포장할 때는 앱 버전과 기존 Git 태그를 유지한다. 포장 변경은 manifest의 `bundleRevision`·생성 시각·SHA-256과 버전 이력에 별도로 기록하며 기존 릴리스 태그를 이동하지 않는다.
