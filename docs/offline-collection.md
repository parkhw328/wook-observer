# 직접 실행 수집과 파일 반입

## 사용 순서

1. 관리자로 로그인하고 **자산 관리 → 수집 결과 업로드** 또는 **점검 대상 → 수집 SH / 결과 업로드**를 연다.
2. **수집 SH 다운로드**로 `observer-collect.sh`를 받는다. 폐쇄망 설치 묶음에도 같은 이름의 파일을 제공한다. 로그인한 USER도 스크립트를 내려받을 수 있다.
3. 파일을 **점검할 Linux 서버**로 옮겨 다음을 실행한다. 중앙 Observer 서버에서 대신 실행하면 중앙 서버의 정보가 수집된다.

```sh
sh observer-collect.sh
# 이미 존재하는 다른 저장 폴더를 지정하는 경우
sh observer-collect.sh /tmp
```

4. 완료 메시지에 표시된 `observer-YYYYMMDDTHHMMSSZ-XXXXXXXX.observer` 파일을 가져온다. 결과는 실행 계정만 읽고 쓸 수 있는 권한 600으로 생성한다. 파일을 편집하거나 줄바꿈을 변환하지 않는다.
5. 업로드 화면에서 **새 자산으로 등록** 또는 **기존 자산**을 선택하고 파일을 첨부한 뒤 **파일 내용 확인**을 누른다.
6. 호스트명·운영체제·OS 지원 상태·수집 시각·실행 계정/UID·수집 건수와 제한을 확인한다. 신규 자산은 관리 이름과 IP/호스트명을 입력한다. **확인한 결과 반영**을 누르면 내부 카탈로그 판정, 점검 이력과 자산 서비스 후보를 함께 저장한다.

SSH 계정·비밀번호·호스트 키는 필요하지 않다. 아직 수집하지 않은 서버도 **점검 대상 → + 파일 업로드 자산**으로 등록하고 수기 운영대장을 먼저 작성할 수 있다. 업로드 자산에는 SSH 점검 시작 버튼 대신 결과 업로드와 수집 SH 버튼을 제공한다. 기존 SSH 자산에도 파일을 반영할 수 있으며 저장된 연결 설정은 그대로 유지한다.

## 지원 범위와 실행 조건

- Linux `/bin/sh`, `ps`, `timeout`, `sha256sum`, `mktemp`, `awk`, `head`, `tail`, `wc`, `date` 등 기본 도구가 필요하다. Java 설치는 요구하지 않는다. 도구를 자동 설치하지 않는다.
- 현재 실행 계정으로 조회한다. 일반 계정과 root 실행 결과에는 접근 범위 차이가 있으며 실제 UID를 보고서에 남긴다. 스크립트가 비밀번호를 묻거나 su/sudo로 자동 전환하지 않는다. 필요한 권한은 현장 운영 절차에 따라 선택한다.
- SSH 수집과 같은 고정 수집 코드를 사용한다. OS·커널·프로세스·설치 RPM·TCP 리스닝/UDP 바인딩을 수집하고, Docker·jcmd·Python 3가 존재하며 접근 가능한 경우 컨테이너·선별 JVM 속성·JAR 메타데이터를 추가한다. Windows와 Kubernetes 수집은 지원하지 않는다.
- 수집 전체 최대 180초, 결과 파일 최대 16 MiB다. 프로세스 4,096개, 컨테이너 256개, JVM 64개, JVM당 라이브러리 512개, RPM 20,000개/4 MiB, 소켓 4,096개/512 KiB 등의 기존 제한을 공유한다.
- 조회 실패·권한 부족·선택 도구 없음은 제한으로 남긴다. 시간 초과·크기 초과·기본 스냅샷 미완료는 성공 파일을 남기지 않는다. 스크립트와 결과를 쓰는 임시 경로는 종료 시 정리한다.
- 패키지 설치, 서비스 시작/종료, 컨테이너 변경, 임의 명령 실행, 환경변수·전체 명령행 수집, 외부 전송은 수행하지 않는다. `jcmd`는 선별 속성 조회를 위한 attach를 사용한다.

## 반영과 보존 규칙

- `.observer`는 형식 버전·수집기 버전·UTC 수집 시각·본문 SHA-256과 고정 텍스트 레코드로 구성한다. 서버는 UTF-8·완료 마커·레코드 종류/건수·크기·해시를 검증한다. ZIP·SH 파일을 실행하거나 업로드 경로로 해석하지 않는다.
- 해시는 전송 손상을 검출하며 파일 작성자나 서버 신원을 인증하는 서명이 아니다. 업로드한 호스트와 선택한 자산이 같은 서버인지 관리자가 확인한다. 기존 관측 호스트명과 다르면 별도 확인 체크가 필요하다. IP/호스트명 변경만으로 다른 자산에 자동 연결하지 않는다.
- 수집 시각과 반입 시각을 구분한다. 대상 시계가 현재보다 10분 이상 미래이거나 2000년 이전이면 반입을 거부하고 시계 확인을 안내한다.
- 자산의 현재 관측값은 실제 수집 시각이 가장 최근인 결과를 사용한다. 과거 파일은 점검 이력에 보존하며 최신 관측·수기 정보·기존 스냅샷을 덮어쓰지 않는다. 서버 시계가 정확해야 한다.
- 같은 파일 전체의 SHA-256을 기준으로 중복 반영을 막는다. 같은 자산 재시도나 신규 등록 재시도는 기존 이력으로 안내하고, 이미 다른 자산에 반영된 파일은 거부한다. 네트워크 응답이 끊겨도 같은 파일로 재시도할 수 있다.
- 반입 시점의 내부 카탈로그로 새 판정을 생성한다. 파일이 주장하는 판정을 받아들이지 않으며, 이전 보고서를 재판정하지 않는다. 단순 중복 재업로드도 재판정하지 않는다.
- 검증·판정·저장 실패 시 자산·서비스·점검 이력 변경을 롤백한다. 점검 중인 자산은 완료 후 반입한다. 수기 프로필·운영대장과 보관 상태는 유지한다.
- ADMIN은 자산 생성/수정과 파일 반입을 수행한다. USER는 스크립트·자산·보고서 조회/다운로드를 할 수 있다. 기존 세션 인증과 CSRF 보호를 적용한다.
- 원본 파일명·내용·명령·자격 증명은 로그에 남기지 않는다. 미리보기/반영/중복 이벤트에 요청 ID·수행자·자산/점검 ID·크기·건수·SHA-256·소요 시간을 기록한다. 원본 업로드 파일은 서버 파일시스템에 별도 보관하지 않으며 저장 스냅샷으로 JSON·MD·XLSX·ZIP을 생성한다. 원본 반입 파일이 필요하면 현장 보관 절차를 따른다.

## API

| 요청 | 기능 |
| --- | --- |
| `GET /api/collector/observer-collect.sh` | 로그인한 사용자에게 독립 실행 SH 제공 |
| `POST /api/admin/offline/targets` | SSH 없는 자산 생성 (`name`, `host`, `description`) |
| `PUT /api/admin/offline/targets/{id}` | 업로드 자산 기본 정보 수정 |
| `POST /api/admin/offline/preview` | multipart `file`, 선택 `targetId` 검증/미리보기 |
| `POST /api/admin/offline/import` | 같은 multipart와 신규 `name`/`host`, 선택 `confirmIdentity`로 원자적 반영 |

기존 자산 관리와 XLSX/Markdown 사용법은 [자산 관리 안내](asset-management.md), 로그 조회는 [운영 로그](operations-logging.md)를 따른다.

## RHEL·CentOS 7.x와 작은 결과 파일

1.11.0은 procps-ng 3.3.10이 쉼표로 연결한 `pid=,ppid=,...`를 헤더로 해석해 PID만 남기는 문제를 수정했다. 각 출력 필드를 개별 `-o` 인자로 조회하며 JVM 탐색에도 같은 방식을 사용한다. 생성 전 프로세스 필드를 검증해 사용할 수 없는 파일을 성공으로 남기지 않는다. 기존 파일에 PID만 있고 계정·메모리·스레드·프로세스명이 없다면 복원 근거가 없으므로 **최신 SH로 다시 수집해야 한다**.

RPM 4.11에서 `MODULARITYLABEL` 지원 여부를 먼저 확인하고 지원하는 태그만 조회한다. 구형 RPM은 미지원 태그 오류를 내고도 종료 코드 0을 반환할 수 있으므로 RPM 결과가 비어 있으면 `FAILED`와 재수집 안내를 남긴다. OS·프로세스 등 필수 자산 근거가 유효하면 RPM·소켓의 부분 실패로 반입 전체를 거부하지 않는다. `ss`는 `-H` 없이 실행하고 알려진 헤더만 제거한다.

`hostname` 명령이 없는 최소 환경에서는 `uname -n`으로 수집한다. 구버전 SH가 만든 파일의 HOST 이름이 비어 있어도, 해시·완료 마커가 유효하고 수집된 `uname -a`에 명확한 Linux 호스트명 근거가 있으면 1.11.0에서 복원한다. 이 경우 복원 출처와 제한을 남긴다. 호스트명 근거까지 없는 파일이나 손상·잘림·다른 형식은 계속 거부한다. 도메인 사용자 이름의 `\`·`@`와 Unicode는 제한된 길이 안에서 허용하고 제어 문자는 거부한다.

Python 3·Docker·jcmd 부재는 기본 자산 반입을 막지 않는다. 설치된 Python 3가 추가 라이브러리 수집 코드를 실행하지 못해도 실패 제한을 기록하고 기본 수집을 유지한다. SH는 호스트명·CPU·실행 계정·프로세스 등 최소 결과를 확인한 뒤에만 파일을 남기고, 종료 메시지에 프로세스/RPM/포트 수를 표시한다.

파일이 작거나 이전 버전에서 “올바르지 않은 형식” 오류가 났다면:

1. 중앙 앱을 1.11.0으로 업데이트하고 같은 버전의 수집 SH를 받는다.
2. 대상 서버에서 `sh observer-collect.sh`를 다시 실행한다. 도구를 임의 설치하거나 원본 결과를 편집하지 않는다.
3. 완료 메시지와 파일 크기, 업로드 **파일 내용 확인**의 호스트/OS/항목 수/수집 제한을 확인한다. 파일이 작은 것 자체는 오류가 아니다.
4. 여전히 실패하면 오류 문구와 원본 `.observer`를 현장 보관 절차에 따라 확인한다. 1.11.0은 헤더·해시·레코드·UTF-8·호스트 근거 오류를 구분해 안내한다.

실제 검증은 CentOS 7.9와 Red Hat UBI 7.9 컨테이너의 구형 사용자 공간·RPM 4.11에서 수행했다. 컨테이너는 시험 호스트의 커널을 공유하므로 물리 RHEL 7 서버 전체나 개별 운영 권한을 검증한 결과는 아니다. OS 수명주기 범위와 ELS 조건은 [OS 지원 정책](os-lifecycle.md)을 따른다.
